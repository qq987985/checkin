SITE CONFIGURATION

添加签到站点

请求方法怎么选？在网络面板里打开实际签到请求 → Headers（请求头）→ General（常规）→ 查看 Request Method：显示 POST 就选 POST，显示 GET 就选 GET，PUT / PATCH 同理。不要根据网址猜测，也不要直接照用默认 POST。

签到地址就是 Request URL。请按下方完整步骤获取，不要填浏览器地址栏里的页面网址。

签到地址和请求方法在哪里获取？

网页签到：从获取 URL 到保存配置（完整步骤）

  1. 登录并打开签到页面：在电脑浏览器登录自己的账号，进入能手动点击「签到」的页面。先不要点击签到。
  2. 打开开发者工具：按 F12（Mac 可按 ⌥⌘I），也可右键网页选择「检查」，打开 Network（网络）面板。
  3. 准备记录请求：选择 Fetch/XHR，点击网络面板的清除按钮，清空已有记录；保持面板打开。若签到会跳转页面，可勾选 Preserve log（保留日志）。
  4. 手动签到一次：回到页面点击「签到」，查看网络面板刚新增的请求。没有看到请求时，切回 All（全部）重新查看。
  5. 确认真正的签到请求：逐条查看新请求的 Response（响应）或 Preview（预览），找到返回签到结果的那一条。checkin、sign 等名称只作线索；不要选图片、统计上报或 OPTIONS 预检请求。
  6. 复制签到地址 URL：打开这条请求的 Headers（请求头）→ General（常规），找到 Request URL，复制完整地址（包括 ? 后的查询参数），粘贴到本工具的「签到接口 URL」。不要复制浏览器地址栏，也不要只复制请求列表里的短名称。
  7. 选择对应的请求方法：在同一条请求的 General（常规）里查看 Request Method：显示 POST 就选择 POST，显示 GET 就选择 GET，PUT / PATCH 同理。URL 和方法必须来自同一条请求，不能根据网址猜测。
  8. 填写验证凭据：在 Request Headers（请求标头）中查看：Cookie 填到 Cookie 验证；Authorization: Bearer 后面的值填到 Bearer Token 验证（不含 Bearer 前缀）；其他 API Key 按原来的请求头名称和值填写。需要多个验证请求头时，在高级配置里填写 JSON 对象。
  9. 核对请求体和结果规则：如原请求有 Payload（请求载荷），按实际格式填写高级配置里的请求体，并核对 Content-Type；再根据实际响应设置成功字段或关键词。没有请求体就选择「无请求体」。
  10. 保存并确认执行结果：设置每日次数与时间后保存。可点击「立即签到」测试，这会实际发送签到请求；若当天已手动签到，可能返回「已签到」。检查运行记录；「待确认」时先核对响应规则，不要直接当作成功。

填写示例（仅演示，不能直接使用）

Request URL: https://example.com/api/checkin
Request Method: POST
对应填写：签到接口 URL = 上面的完整网址；请求方法 = POST。两项必须来自同一条实际签到请求。如果看不到 Request Method，先确认打开了请求详情，不要猜选。

豆包 App：与网页获取方式不同

需要从手机 App 实际点击签到时的网络请求获取 URL、HTTP Method（请求方法）、请求头和请求体；电脑端豆包首页或火山方舟模型 API 地址不能代替它。可使用支持该设备的网络调试工具查看自己账号的签到请求。若无法获取请求，暂时无法配置自动签到。

如果请求包含动态签名、设备校验或一次性参数，复制地址和 Token 仍可能无法重放，需要专门适配。

可右键网页请求 → Copy → Copy as cURL，便于核对地址、方法、请求头和请求体。完整 cURL 可能含登录凭据，请只在本机保存和填写。

验证方式怎么选？查看真实签到请求的 Headers（请求头）→ Request Headers（请求标头），按实际携带的凭据选择，不能根据站点名称猜测。

验证方式判断与凭据填写说明
  1. 登录目标网站，打开 Network（网络）面板，清空记录后手动签到一次。
  2. 找到返回签到结果的实际请求，打开 Headers → Request Headers；不要看成 Response Headers（响应头）。
  3. 按下面的对应关系选择验证方式，并复制你自己账号的实际凭据。

Cookie

看到 Cookie: session=…; other=…：选择「Cookie」，复制冒号后面的整段值，包含各个键值对及分号，不包含 Cookie: 字样。不要复制响应里的 Set-Cookie。

CookieCloud 自动获取 Cookie

已安装 CookieCloud 扩展的用户，可先在页面顶部配置服务器地址、用户 KEY / UUID 和端对端密码，再为站点选择「CookieCloud」。浏览器保持「上传到服务器」模式并手动同步一次；工具会在每次执行签到前下载密文、本机解密并按签到 URL 自动匹配 Cookie。它不会自动识别签到地址或获取手机 App 的 Cookie。

Bearer Token

看到 Authorization: Bearer abc…：选择「Bearer Token」，只填 abc…，不要重复填写 Bearer 前缀，工具会自动补上。

API Key / 自定义 Token 请求头

看到 X-API-Key: abc… 或 token: abc…：选择「API Key」，请求头名称照填 X-API-Key 或 token，凭据填冒号后面的值。名称和值都以实际请求为准。

其他 Authorization 或多个验证头

例如 Authorization: Basic …，或同时要求 Cookie、Token、设备参数：选择「无需验证 / 使用自定义请求头」，在高级配置的「自定义请求头」中填写完整 JSON。此选项也用于手工配置验证，不代表该接口无需登录。

示例仅演示结构：{"Cookie":"session=你的值","Authorization":"Basic 你的值"}。也可选择 Cookie / Bearer / API Key 并在自定义请求头里补充其他不同名称的请求头；同名请求头以所选验证方式生成的值为准。

没有看到这些请求头？

继续检查 Request URL 的查询参数和 Payload（请求载荷）；Token 可能在这些位置。若凭据在 URL 中，保留完整 URL；若在请求体中，按原格式填写请求体与 Content-Type。URL、请求头和请求体可能同时参与验证，不能只复制其中一项。

请求头没有凭据并不能说明无需验证。只有确认原请求不依赖登录凭据时，才按免验证接口配置；无法确定时先核对接口文档或完整请求，不要猜选。

保存后如何确认？

保存后点击「立即签到」会真实执行请求，查看运行记录。401 / 403 常提示认证或权限问题，也可能涉及签名、设备校验等要求；仅凭状态码无法确定具体原因。HTTP 200 也不代表签到成功，应按响应配置成功字段或关键词；「待确认」需要核对规则。

豆包 App 等接口若需要动态签名、设备校验、一次性参数或验证码，仅复制静态 Cookie / Token 可能无法运行，本工具不会自动生成这些参数。凭据过期后需从新请求中重新获取。

Cookie、Token、含凭据的 URL 和完整 cURL 都可能包含登录信息，请只在自己的管理页面填写，不要公开发送。编辑已有站点时，凭据留空会保留原值。

从全局 CookieCloud 设置读取最新 Cookie，按上方签到 URL 自动匹配域名与路径。请先点击页面顶部的 CookieCloud 设置完成连接；无需手工填写 Cookie。

多个时间用英文逗号分隔。每个时间点执行一次，达到每日成功次数后停止；失败时在后续时间点重试。次数多于时间点时，需手动执行补足。
